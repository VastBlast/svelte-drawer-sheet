# Animation Performance

Each visual frame, the browser must finish JS → style → layout → paint → composite within the frame budget (~16ms at 60Hz, ~8ms at 120Hz). Animations feel laggy for a small number of underlying reasons:

1. Frames are generated by something that can be throttled or blocked (usually main-thread JS).
2. Each frame costs too much layout or paint work.
3. Other work competes for the thread at the wrong moment.
4. The animation can't respond to input mid-flight.

Every rule below traces to one of these. They are preferences, not absolutes; a real constraint can override one, but know which cost you're accepting.

## 1. Who generates the frames (the biggest lever)

Prefer declaring start and end and letting the browser interpolate (CSS transitions, CSS animations, WAAPI) over generating frames in JS (rAF loops, spring/tween libraries writing styles every frame).

Browser-driven animation runs on the browser's own timeline, and when it touches only compositor properties it continues at full rate even while the main thread is busy. JS-driven animation depends on both the main thread and `requestAnimationFrame`, which browsers throttle: iOS Low Power Mode caps rAF near 30fps, background tabs pause it, long tasks block it. Browser-driven motion degrades gracefully; JS-driven motion inherits every stall.

```js
// Prefer: write the destination once per state change; the browser interpolates
el.style.transform = `translate(${x}px, ${y}px)`;
// .el { transition: transform 300ms cubic-bezier(0.22, 1, 0.36, 1); }

// Over: a per-frame loop producing the same motion
function tick() {
    current += (target - current) * 0.15;
    el.style.transform = `translate(${current}px, 0)`;
    requestAnimationFrame(tick);
}
```

Per-frame JS is legitimate when the target changes continuously (gesture-following, drag physics, scrubbing). Then keep the per-frame path minimal:

- Prefer one direct, cheap style write (`transform`/`opacity`, or a CSS variable consumed by one element) over routing the value through component state. A value that changes 60 times a second should not run the framework's render cycle.
- Prefer rAF over `setInterval`/`setTimeout`: timers aren't frame-aligned, so motion tears.
- Prefer handing off to the browser once the gesture ends (on release, play a transition or `element.animate` to rest) over simulating the settle in JS. For spring feel without per-frame JS, pre-compute the spring curve into a `linear()` easing or generated keyframes.

## 2. What each frame costs

Prefer animating `transform` and `opacity` over properties that re-run layout (`width`, `height`, `top`/`left`, `margin`, `padding`, `font-size`, `flex-basis`, `grid-template-*`) or heavy paint (`box-shadow`, `filter: blur()`, `backdrop-filter`, large gradients).

Compositor properties move an already-rasterized texture, so cost stays flat regardless of what's inside or around the element. A layout property re-lays-out everything that depends on it, every frame: tolerable on a small isolated pill, catastrophic on a sidebar whose width reflows the whole page. Paint-heavy properties re-rasterize pixels every frame, and cost scales with area.

- Prefer `translate` over animating `left`/`top`.
- Prefer FLIP for layout changes (measure First and Last positions, Invert with a transform, Play the transform back to zero) over transitioning the layout property itself.
- Prefer `scale` or a clip/mask reveal over animating `width`/`height` when the visual allows it.
- Prefer explicit property lists over `transition: all`, which silently animates properties you never intended.
- When a layout property genuinely must animate (true reflow, e.g. an accordion pushing content), prefer a browser-driven transition on a small subtree with `contain: layout paint` on the animated element, so the damage is bounded and the browser still owns the frames.

## 3. Measure once, then write

Prefer batching all layout reads (`getBoundingClientRect`, `offsetWidth`, `scrollTop`) before all style writes, once per state change, over interleaving reads with writes or measuring inside the frame loop. A layout read after a style write forces synchronous layout; interleaved in a loop, layout runs multiple times per frame (layout thrashing).

```js
// Prefer: read everything, then write everything
const a = elA.getBoundingClientRect();
const b = elB.getBoundingClientRect();
elA.style.transform = `translate(${a.width}px, 0)`;
elB.style.transform = `translate(${b.width}px, 0)`;

// Over: write, then read, then write
elA.style.width = `${w}px`;
const left = elB.offsetLeft; // forced synchronous layout
elB.style.left = `${left}px`;
```

Prefer event-driven re-measurement (ResizeObserver, known mutation points) over polling.

## 4. Keep the thread clear while it matters

A cheap animation still stutters if a long task lands during it, and a dropped first frame is the one users read as input lag.

- Prefer sequencing heavy work around motion: run the transition, then mount or process the expensive content, or finish the work first and then animate. Animating a panel open while simultaneously rendering its heavy contents janks both.
- Prefer CSS-owned scroll effects (`position: sticky`, scroll-snap, scroll-driven animations) over scroll handlers writing styles. Scroll events arrive asynchronously to composited scrolling, so handler-driven effects visibly trail the finger.
- Prefer pausing ambient loops (shimmer, pulse, marquee, spinners) when off-screen or obscured, via IntersectionObserver or `animation-play-state`, over letting them run forever.
- Prefer animating one container over N children each running an independent animation, and prefer staggering only the visible items of a long list over an entrance animation on every row.

## 5. Layers: few and deliberate

- Prefer promoting only what animates, for the duration it animates (`will-change` added before and removed after, or an existing transform), over sprinkling `will-change` widely. Each layer costs memory, and overpromotion slows compositing and can blur rasterized content.
- Prefer one moving layer over multiple elements that must stay in per-frame sync (counter-transforms, duplicated content moving oppositely). Synced layers multiply per-frame work, and any desync reads as wobble. Blend modes, masks, clipping, or restructuring often collapse the effect into a single layer.
- Prefer keeping expensive pixels off the moving layer: `backdrop-filter` re-filters against a changing backdrop on every frame of movement, and large blurs or oversized shadows inflate what must be rasterized and composited. Put the shadow on a static wrapper or crossfade a pre-blurred copy.

## 6. Handle interruption and instant states

An animation that ignores the user feels laggy even at a perfect frame rate.

- Prefer mechanisms that retarget from the current position mid-flight (transitions, springs) over keyframes that restart from zero, for anything re-triggerable in quick succession: tabs, toggles, toasts, hover.
- Prefer letting input land during motion over locking interaction until it completes.
- Prefer an explicit instant path alongside the animated one: first paint, container resize, orientation change, and programmatic corrections should snap with no transition. An indicator that animates on window resize, or slides in from (0, 0) on mount, reads as a glitch.

```css
.indicator { transition: transform 300ms ease-out; }
.indicator.instant { transition: none; } /* applied for mount/resize syncs */
```

- Prefer `@starting-style`, WAAPI, or a two-frame wait for entrance transitions over inserting an element and its final class in the same frame; style resolves once, and the transition silently never plays.

## 7. Verifying smoothness

You can rarely feel an animation yourself, so never report motion as smooth just because the code runs.

- Prefer verifying architecturally over claiming empirically: check the code against the causes above (frame source, per-frame cost, contention, interruptibility). They predict behavior under load.
- Prefer recommending stress testing to whoever can run it, over dev-machine spot checks: fast hardware makes every approach look identical, and differences appear only under throttling. Useful conditions to suggest: iOS Low Power Mode (instantly separates browser-driven from JS-driven motion), a 4-6x CPU throttle in DevTools, and interacting while the app is busy (mid-load, mid-scroll) rather than idle.
